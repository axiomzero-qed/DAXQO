# DAXQO V0.5：任务规划与助手转交

V0.5 聚焦把清楚的长任务交给本机 DAXQO Harness 持续执行。继续使用 STEPX Neo 现有 Linux 环境；本版本不迁移到 Termux。

## 任务规划

规划先形成一份简短、可公开复核的计划，列出目标、步骤、完成条件和结果核验方法。涉及手机应用时，先检查并优先使用已安装的 App；确实缺少时再通过设备商店安装。登录和权限按正常系统界面及用户本机号码流程完成。执行后核对真实页面或产物，并如实记录失败；不把计划文本当作完成证明。

新任务启动时会收到设备型号、Android 版本、控制就绪状态、商店和最多 80 个可启动应用的紧凑清单；快照缓存 60 秒。`android_apps` 可按名称或包名查询，清单不可用或被截断不代表应用缺失。快照不读取账号、手机号、坐标或模型密钥。重启后恢复的会话也会收到当前指令；已经加载的旧会话应通过工具重新核对变化。

机主偏好已写入系统指令：一般拒绝通知、营销和无关权限；任务需要定位时直接允许，默认仅使用期间，附近与导航可用精确定位；优先复用已登录账号，否则优先本机号码一键登录和正常短信自动填充。偏好遵守手机当前 `full` / `confirm` 授权模式，实际需要审批时等待一次确认，确认后由达序继续执行。不会为可正常使用的 App 先做无关更新。

## 助手转交

本机 MCP stdio 客户端提供 `daxqo_submit`、`daxqo_status`、`daxqo_continue`、`daxqo_stop`。提交要求稳定唯一的 `requestId`；成功返回 task ID 只表示 Harness 已接单，不表示任务完成。客户端通过本机 `assistant_client.py` 启动 MCP stdio 服务，不要求语音助手本身直接实现 MCP。

转交 Skill 通过现有 OpenClaw/StepClaw 设备 bash 通道 `stepclaw.exec` 调用手机上的 CLI。安装器默认只预览；确认目标为现有 workspace skills 目录后，使用 `--install` 写入 `daxqo-handoff/SKILL.md`。不同的已有同名文件会先保留备份；不会改动厂商认证、端口或 MCP 配置，也不会自动发送模型消息。详见 `scripts/install_assistant_skill.py --help`。

### 最简安装与调用

1. 在已运行的手机 Linux 中从本版源码运行 `python3 scripts/install_linux.py`，安装对应 V0.5 APK，沿用已有配对和手机控制授权。已有受管安装可使用带哈希校验、检查和回退的更新入口；不要重建 Linux。
2. 具有 MCP 客户端能力的程序可参考仓库根目录 `mcp-config.example.json`。服务通过 stdio 启动，只访问已配对的本机 DAXQO；不要把配对文件复制到云端或把现有服务端口直接暴露到公网。
3. 为当前 STEPX 助手安装 Skill，在手机 Linux 执行：

```sh
python3 /root/phone-harness/install_assistant_skill.py
python3 /root/phone-harness/install_assistant_skill.py --install
```

现有 Skills 目录须已经存在。安装后新建助手对话，明确说“用达序的长任务转交技能，把……交给达序，接单后告诉我任务号”，给出完整目标与约束；也可明确指定 `daxqo-handoff` 技能。仅说“交给达序”不能保证原生助手选中该技能。直接测试同一个 MCP 客户端：

```sh
python3 /root/phone-harness/assistant_client.py daxqo_submit --args '{"prompt":"在工作区写一份简短待办并读取核验","title":"待办","requestId":"replace-with-a-new-uuid"}'
python3 /root/phone-harness/assistant_client.py daxqo_status --args '{"taskId":"returned-task-uuid","offset":0,"limit":2000}'
```

同一提交遇到超时保留原 `requestId`，不要用新 ID 重复建任务。查询结果通过 `resultNextOffset` 继续分页。`daxqo_continue` 用新的稳定请求 ID 追加要求，`daxqo_stop` 请求停止；二者不提供绕过机主审批的接口。GUI 可继续查看、补充或停止同一个任务。文件成果可从达序文件页查看。

## Task planning and assistant handoff

V0.5 focuses on handing clear, long-running work to the local DAXQO Harness. It continues to use STEPX Neo's existing Linux environment and does not migrate to Termux.

Planning produces a short, reviewable public plan with the goal, steps, completion conditions, and verification method. For phone tasks, check for and prefer apps already installed; install from the device's app store only when needed. Use normal system permission screens and the user's local phone-number login flow. Verify the actual screen or artifact afterward and report failures honestly; a plan is not proof of completion.

New tasks receive a compact snapshot of the device model, Android version, control readiness, stores, and up to 80 launcher apps, cached for 60 seconds. `android_apps` can query names or package IDs. An unavailable or truncated catalog does not prove an app is missing. The snapshot reads no accounts, phone numbers, coordinates, or model keys. Threads resumed after restart receive current instructions; already loaded older threads should recheck changes using tools.

Owner preferences are part of the system instructions: generally decline notifications, marketing, and unrelated permissions; allow task-relevant location, normally while in use, with precise location for nearby places and navigation. Reuse an existing login, otherwise prefer legitimate one-tap SIM-number login and normal SMS autofill. These preferences retain the phone's `full` / `confirm` policy: wait for actual required approval, then let DAXQO perform the action. Skip unrelated updates when an installed app is usable.

The local MCP stdio client exposes `daxqo_submit`, `daxqo_status`, `daxqo_continue`, and `daxqo_stop`. Submission requires a stable unique `requestId`. A returned task ID means the Harness accepted the request, not that it finished. The on-device `assistant_client.py` starts the MCP stdio service, so the voice assistant itself does not need native MCP support.

The handoff Skill calls the phone CLI through the existing OpenClaw/StepClaw device bash channel, `stepclaw.exec`. The installer previews by default. After confirming the existing workspace skills directory, use `--install` to write `daxqo-handoff/SKILL.md`. A different existing file with the same name is backed up before replacement. The installer does not change vendor authentication, ports, or MCP configuration, and does not send a model message. See `scripts/install_assistant_skill.py --help`.

### Minimal installation and use

1. Run `python3 scripts/install_linux.py` from this source version inside the phone's existing running Linux environment, install the matching V0.5 APK, and retain existing pairing/control grants. Managed installations can use the update path with hashes, checks, and rollback. Do not rebuild Linux.
2. MCP-capable clients can use the root `mcp-config.example.json` as an example. The stdio server accesses only the paired local DAXQO service. Do not copy the pairing file to a cloud client or expose the existing service ports to the public internet.
3. Preview and install the STEPX handoff Skill using the two `install_assistant_skill.py` commands above. Its existing Skills directory must already exist. Start a fresh assistant conversation and explicitly name the long-task handoff Skill, including the full goal, constraints, and a request for its task ID. Both the Chinese phrase above and explicitly naming `daxqo-handoff` passed on this phone. A plain “hand this to DAXQO” does not reliably select the native assistant's skill. The CLI examples above exercise the same MCP client directly; replace the request ID for each new request and use the returned task UUID for status.

After an uncertain timeout, retain the original `requestId` instead of creating a duplicate task. Follow `resultNextOffset` for result pages. `daxqo_continue` adds instructions with a new stable request ID; `daxqo_stop` requests cancellation. Neither provides an owner-approval bypass. The GUI can inspect, continue, or stop the same task and display its files.

The first plain “hand this to DAXQO” request instead made Amoo write a file in its own workspace, with no DAXQO submission. That attempt failed acceptance. Explicitly naming the Skill passed. Native skill selection still depends on the conversation and wording; inventory discovery alone does not prove that the session selected it.

**Not yet verified:** the complete microphone/ASR-to-submission path, automatic handoff for arbitrary natural wording, long-duration stress or 24-hour operation, other devices, and new-account one-tap number/SMS login. Location, notification, and login preferences are injected, but no extra permissions or accounts were created just for testing.

This release does not claim that arbitrary MCP servers can be configured in Amoo or that the vendor Linux container will stay online for 24 hours. The task service may be unavailable while that container is stopped.
