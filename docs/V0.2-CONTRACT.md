# DAXQO 达序 V0.2 接口与架构（历史规范） / DAXQO V0.2 API and Architecture (Historical Contract)

> 本文记录 V0.2 的历史接口行为，不代表 V0.3 的当前功能或限制。 / This document records historical V0.2 API behavior; it does not define V0.3 features or limitations.

## 运行架构 / Runtime architecture

DAXQO 后端提供本机任务 API，监听 `127.0.0.1:18880`。运行控制桥监听 `127.0.0.1:18882`，负责查看服务状态及管理后端运行与更新。两个服务共享安装目录中的私有状态和 capability；控制桥不承担任务对话或模型请求。

The DAXQO backend provides a local task API on `127.0.0.1:18880`. The runtime-control bridge listens on `127.0.0.1:18882` to report service status and manage backend lifecycle and updates. Both services share private state and a capability within the installation directory; the bridge does not handle task conversations or model requests.

当前 Android 运行方式依赖终端提供的 ARM64 Linux 容器。控制桥可在该环境中管理后端，但这不代表 DAXQO 已脱离终端容器运行。

The Android runtime described here depends on the ARM64 Linux container provided by the terminal app. The bridge can manage the backend inside that environment, but this does not mean DAXQO runs independently of the terminal container.

后端 API 使用 capability Bearer token，并校验 Host 与 Origin。状态及对话接口不返回 provider API key。provider 凭据保存在私有状态目录，不应放入源码或日志。

The backend API uses a capability Bearer token and validates Host and Origin. Status and conversation endpoints do not return the provider API key. Provider credentials are stored in a private state directory and must not be placed in source code or logs.

## 对话接口 / Conversation API

在 V0.2 中，一个 task 表示持续会话，具有稳定的 task ID，并复用同一个 Codex thread ID。

In V0.2, a task represents a persistent conversation, has a stable task ID, and reuses the same Codex thread ID.

- `POST /api/tasks` 创建任务和首条消息。请求：`{ "prompt": "...", "title": "可选", "model": "可选" }`。返回新建的 task。

  `POST /api/tasks` creates a task and its first message. Request: `{ "prompt": "...", "title": "optional", "model": "optional" }`. It returns the created task.
- `GET /api/tasks` 返回任务列表；`GET /api/tasks/<id>` 返回任务详情与执行事件。

  `GET /api/tasks` returns the task list; `GET /api/tasks/<id>` returns task details and execution events.
- `GET /api/tasks/<id>/messages` 返回 `{ "messages": [...] }`。消息按发送顺序排列，含 `id`、`role`、`text`、`createdAt`、`status`，可含 `turnId`；user 消息还含 `clientMessageId`。旧任务的首条 prompt 和已有结果可迁移显示。

  `GET /api/tasks/<id>/messages` returns `{ "messages": [...] }`. Messages are ordered by send time and contain `id`, `role`, `text`, `createdAt`, and `status`, with an optional `turnId`; user messages also contain `clientMessageId`. A legacy task's initial prompt and existing result can be shown after migration.
- `POST /api/tasks/<id>/messages` 追加消息。请求：`{ "text": "...", "clientMessageId": "客户端生成的稳定标识" }`。返回 `{ "task", "message", "delivery" }`，`delivery` 为 `steered`、`started` 或 `queued`。

  `POST /api/tasks/<id>/messages` appends a message. Request: `{ "text": "...", "clientMessageId": "stable client-generated identifier" }`. It returns `{ "task", "message", "delivery" }`, where `delivery` is `steered`, `started`, or `queued`.

同一 task 中的 `clientMessageId` 是幂等键。相同标识不会创建第二条消息或重复执行；已成功或处理中消息返回原状态，失败记录按下述重试规则处理。消息状态包括排队中 `queued`、发送中 `sending`、已接收 `steered` 或 `started`，以及失败 `failed`；assistant 回复只在收到 native turn 完成通知后持久化为完成消息。

Within a task, `clientMessageId` is an idempotency key. Reusing an identifier does not create a second message or execute it again; successful or in-progress messages return their existing state, while failed records follow the retry rules below. Message states include queued (`queued`), sending (`sending`), accepted (`steered` or `started`), and failed (`failed`). An assistant reply is persisted as complete only after a native turn-completion notification.

追加消息时，若当前 turn 可接收输入，服务端以当前 turn ID 设置 native `turn/steer` 的 `expectedTurnId`。客户端无需提交该字段；若客户端提供，服务端会校验它与当前 turn 一致。当前 turn ID 尚未就绪时，消息会持久排队。task 空闲或已完成时，服务端在原 thread 上启动后续 turn；新启动的 app-server 进程会先通过 `thread/resume` 加载保存的 thread。

When the current turn can accept input, the server sets the native `turn/steer` `expectedTurnId` to the current turn ID. Clients do not need to provide this field; if they do, the server verifies it matches the current turn. Messages are durably queued while the current turn ID is not yet available. When a task is idle or complete, the server starts a subsequent turn on the original thread; a newly started app-server process first loads the saved thread through `thread/resume`.

V0.2 中，如果另一 task 正在执行，追加消息会被拒绝，以避免发送到错误会话。明确收到 native RPC 拒绝的失败消息可用原 `clientMessageId` 显式重试：`{ "text": "原消息", "clientMessageId": "原标识", "retry": true }`。超时或断连无法确定 native 是否已接收，不会自动重发，也不允许以该标识盲目重试。客户端应将失败状态展示为失败，并保留原标识以便处理明确可重试的消息。以上单任务并发规则仅描述 V0.2，不应套用于 V0.3。

In V0.2, appending a message is rejected while another task is running, to prevent delivery to the wrong conversation. A message that failed after an explicit native RPC rejection may be retried with its original `clientMessageId`: `{ "text": "original message", "clientMessageId": "original identifier", "retry": true }`. After a timeout or disconnect, native receipt is uncertain: the server does not resend automatically and does not allow a blind retry with that identifier. The client should show the failed state and retain the identifier for messages explicitly known to be safe to retry. This single-active-task concurrency rule describes V0.2 only and must not be applied to V0.3.

## 状态与其他接口 / Status and other APIs

`GET /api/status` 返回服务、引擎、账户和 provider 状态，并包含 `app: { "name": "DAXQO", "version": "0.2.0" }`。provider、models、files、approvals 与 engine/reconnect API 保持现有行为及 capability/Origin 校验。

`GET /api/status` returns service, engine, account, and provider status, including `app: { "name": "DAXQO", "version": "0.2.0" }`. The provider, models, files, approvals, and engine/reconnect APIs retain their existing behavior and capability/Origin validation.

任务可通过 `POST /api/tasks/<id>/stop` 请求停止；已中断任务可通过 `POST /api/tasks/<id>/resume` 在原 thread 上恢复。工作区文件接口受 workspace 路径限制。

A task can be asked to stop through `POST /api/tasks/<id>/stop`; an interrupted task can resume on its original thread through `POST /api/tasks/<id>/resume`. Workspace file APIs are restricted to workspace paths.
