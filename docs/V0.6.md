# V0.6 语音草稿与成果交付 / Voice drafts and artifact delivery

0.6.1 核心 Android versionCode 为 11；可选独立 Collector 与 Motor 扩展分别使用 versionCode 12、13。本次两机安装的是包含两项扩展、versionCode 13 的组合包，可从现有 versionCode 10 直接覆盖升级。两台真机的升级与下述部分验收已完成。

The 0.6.1 core Android versionCode is 11; the optional independent Collector and Motor extensions use versionCodes 12 and 13, respectively. The combined APK installed on both phones includes both extensions and uses versionCode 13, allowing an in-place upgrade from versionCode 10. The upgrade and the partial device checks below have been completed on both phones.

## 中文

- 语音输入优先使用 Android 本机 `SpeechRecognizer`。本机缺少可用识别服务时，可改用系统提供的语音服务；系统服务可能联网，使用前会提示。功能需要麦克风权限；没有可用服务时会明确报错。
- 语音转写只回填到可编辑草稿，不会自动发送。音频不会直接发送给 DeepSeek。网页语音按钮需新版原生 APK 提供的桥接；本机麦克风识别验收未通过，详见下文。
- GUI 可显示模型返回的工作区文件和目录链接。栅格图片通过已授权接口预览；普通二进制文档可调用原生系统阅读器打开；浏览器则下载后由用户选择应用。SVG 和 HTML 文件只提供下载或纯文本查看，不嵌入网页或活动图像。
- 远程邮件只附加该联系人的已完成或终止任务结果所引用的文件与目录，不扫描整个工作区。单个文件以及每批邮件附件的原始文件合计均不得超过 20 MiB。多封邮件会编号发送；若某封中途送达结果不确定，不会盲目重发。
- 超过大小限制、发送期间发生变化或属于凭据文件的项目会跳过并说明。现有权限、可信联系人及联系人授权边界保持有效。

## 两机真机验收（0.6.1，部分完成）

设备为 Android 16 STEPX Neo（Standard，`io.daxqo.app`）和 Redmi K70（XM，`io.daxqo.xm`）。两机均从已安装的 versionCode 10 直接覆盖安装 versionCode 13 的 0.6.1 APK，保留 Collector 与 Motor 扩展；未卸载旧版。后台更新到 0.6.1 后自动测试通过：XM 为 219 项全通过；Neo 为 219 项，其中 2 项因测试宿主禁止创建 FIFO/socket 而跳过。`/dev/null` 真实字符设备拒绝检查仍保留并通过。

真实交付链路使用本人 Gmail 向两台手机各自已配置的 163 收件邮箱发起任务。每台手机生成 PNG、PDF 和两个各 11 MiB 的二进制文件；仅两个二进制文件合计 22 MiB，计入 PNG 与 PDF 后总附件量略高于 22 MiB。按每批不超过 20 MiB 分成两封编号邮件 `[1/2]`、`[2/2]`。Gmail 每台设备均收到两封邮件、共 4 个附件。下载核对确认 XM 图片与 Neo PDF 字节与对应成果一致；没有核验两个二进制附件的接收字节或逐一核验全部附件哈希。

两机 GUI 中的目录链接、列出 4 个文件的目录内容及点击图片后展开的大图均已截图确认。两机均通过系统应用选择器选择 WPS 打开 PDF，实际看到对应的 `DAXQO DEVICE TEST - NEO` / `DAXQO DEVICE TEST - XM` 页面。通用下载类型会按文件扩展名回落为 PDF 等实际 MIME 类型，供系统选择合适的阅读器。

聊天图片闪烁已复现并修复：轮询现在保留已有消息和图片节点，仅更新变化的正文、附件版本和送达状态。修复前约 12 秒录屏中，K70 出现 7 帧图片空白、Neo 出现 5 帧；修复后两机各约 20 秒录屏均未出现图片空白。Chrome DOM 回归同时验证了轮询、追加消息、文字增量和重试时复用图片，图片版本变化与切换任务仍正确更新。

语音输入未通过：两机 DAXQO 均已获麦克风权限，实际播放普通中文测试句后都返回 `ERROR 9`，未产生转写。需先确保设备上有可用的语音识别服务再复测；权限已授权时的错误提示已修正，不应反复请求授权。以上不构成 V0.6.1 全量真机验收。

## English

- Voice input prefers Android's on-device `SpeechRecognizer`. If no on-device recognition service is available, a system speech service may be used and the user is warned that it may connect to the network. Microphone permission is required; absence of an available service produces a clear error.
- Transcription fills an editable draft and is never sent automatically. Audio is not sent directly to DeepSeek. The web voice button requires the bridge in a newer native APK; on-device microphone recognition did not pass acceptance, as detailed below.
- The GUI can show workspace file and directory links returned by the model. Raster images are previewed through the authorized endpoint. Ordinary binary documents can be opened with the native system reader; in a browser they are downloaded for the user to open with a suitable app. SVG and HTML files can only be downloaded or viewed as plain text; they are not embedded as web pages or active images.
- Remote email attaches only files and directories referenced by the results of that contact's completed or terminal tasks; it does not scan the whole workspace. Each file and the combined raw attachments in each batch are limited to 20 MiB. Multiple emails are numbered. If delivery of one email is uncertain midway, it is not blindly resent.
- Items over the limit, changed during sending, or identified as credential files are skipped with an explanation. Existing permission, trusted-contact, and contact-authorization boundaries remain in effect.

## Two-device acceptance (0.6.1, partial)

The devices were an Android 16 STEPX Neo (Standard, `io.daxqo.app`) and a Redmi K70 (XM, `io.daxqo.xm`). The 0.6.1 core uses versionCode 11; the optional Collector and Motor extensions use 12 and 13. Both phones received the combined APK at versionCode 13 as an in-place upgrade from installed versionCode 10, retaining the extensions; neither app was uninstalled. After the backend update to 0.6.1, automatic tests passed: XM passed all 219 tests; Neo passed 219 tests with 2 skipped because the test host denied FIFO/socket creation. The `/dev/null` real character-device rejection check remains enabled and passed.

For real artifact delivery, the owner's Gmail submitted a task to each phone's configured 163 mailbox. Each phone produced a PNG, PDF, and two 11 MiB binary files; the binary files total 22 MiB, and the PNG/PDF make the complete attachment set slightly larger than 22 MiB. The files were sent in two messages, numbered `[1/2]` and `[2/2]`, respecting the 20 MiB per-batch limit. Gmail received both messages and all 4 attachments for each device. Download checks confirmed that the XM image and Neo PDF bytes matched their corresponding outputs; the received bytes of the binary attachments were not checked, and hashes were not verified for all attachments.

Screenshots confirmed directory links, four listed files in each directory, and the expanded large image after clicking it in both GUIs. Both PDFs opened through the system app chooser in WPS and displayed the corresponding `DAXQO DEVICE TEST - NEO` / `DAXQO DEVICE TEST - XM` page. Generic download types fall back to the filename's actual MIME type so Android can offer suitable readers.

Chat image flicker was reproduced and fixed by retaining existing message/image nodes during polling and updating only changed text, artifact versions and delivery status. Approximately 12-second baseline recordings contained 7 blank-image frames on K70 and 5 on Neo; neither device's approximately 20-second recording after the fix contained blank-image frames. Chrome DOM regressions also verified image reuse during polling, appended messages, streamed text and retries, while artifact-version changes and task switches still update correctly.

Voice input did not pass: microphone permission was granted on both phones, but playing an ordinary Chinese test phrase returned `ERROR 9` on each and produced no transcription. Retest after a usable speech-recognition service is available. The error message for an already-granted microphone permission was corrected so it no longer asks the user to repeat authorization. These results do not constitute full V0.6.1 device acceptance.
